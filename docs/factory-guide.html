User guide

Software, Manufactured by AI.

Factory-Engineered. Cronos AI is a local-first AI software factory for autonomous planning, code synthesis, and end-to-end workflow validation.

Local-first Human approvals Python 3.12+

Based on Zach Lloyd ideas

!

Current integration boundary. cronos-ai run validates and queues a request. The current controller maintains its lifecycle and processes queued human actions, but does not yet turn queued requests into a complete plan-to-delivery run automatically. The planning, worker, task-recovery, review, webhook, and CI/CD components are available as APIs and are exercised together in tests; task recovery is not yet invoked by the CLI controller.

01 · Get ready

Prerequisites

For the CLI, install Python 3.12 or newer, Git, uv, and the OpenSpec CLI.

Install the locked dependencies

From this repository checkout, run:

uv sync --locked

Herdr, Pi, Docker, profile resources, and a provider API key are needed only when configuring worker execution.

Before enabling workers, read the sandbox guide and Pi, Herdr, and profile guide.

02 · Set the target

Prepare a target repository

The factory only accepts an explicit Git repository root with a clean working tree and initialized OpenSpec.

Initialize OpenSpec for the chosen repository

uv run cronos-ai init --repo /absolute/path/to/repository

This command initializes OpenSpec only when needed and does not modify a different checkout.

Check the command options with uv run cronos-ai init --help.

03 · Submit work

Queue a request

Submit a request by naming both the target repository and requested outcome:

uv run cronos-ai run --repo /absolute/path/to/repository --request "Improve the settings page"

The command validates the target and stores the request in the local SQLite queue.

It does not infer whether the work is actionable, needs detailed specifications, needs clarification, or should be parked. Those decisions belong to the triage workflow.

04 · Keep it running

Run the local controller

Start the controller in the foreground:

uv run cronos-ai controller start

The controller owns a process lock, reports heartbeats, requeues interrupted human-action records, and processes queued human actions. Stop it with Ctrl+C. Restart it with the same state directory to retain queued requests and actions.

Worker-task recovery is available through TaskRecoveryManager, but the CLI controller does not yet run that component automatically.

Inspect the controller and queued work with:

uv run cronos-ai status

The default local state directory is $XDG_STATE_HOME/cronos-ai when XDG_STATE_HOME is set, or ~/.local/state/cronos-ai otherwise.

On first use of the default location, Cronos AI moves an existing ai-software-factory state directory to the corresponding cronos-ai location. The migration preserves the full directory, including factory.sqlite3, its schema, queued requests, and human actions.

If both default directories exist, Cronos AI stops with an actionable error and leaves both unchanged. Back up both directories, choose the authoritative state, then move the other directory out of the state root before restarting.

Use --state-dir /path/to/state or CRONOS_AI_STATE_DIR to select a custom location; either explicit override bypasses default-path migration.

AI_SOFTWARE_FACTORY_STATE_DIR is not recognized. If you previously used that variable, set CRONOS_AI_STATE_DIR to the same custom state path.

05 · Human oversight

Human attention and recovery

List requests and tasks that need a human decision with:

uv run cronos-ai attention

Tasks waiting only for dependencies stay queued and are not reported as human blockers. Use uv run cronos-ai attention --json for machine-readable output.

The queue shows the reason, latest result, and next action for clarification, plan approval, eligible retries, merge conflicts, and run-level review.

Answer a request clarification

Use the request ID shown by the queue:

uv run cronos-ai action --action clarify-request --target <request-id> --data "answer=Describe the clarification"

For a task clarification, include its run ID:

uv run cronos-ai action --action clarify-request --run <run-id> --target <task-id> --data "answer=Describe the clarification"

Approve a plan or retry a task

Approve an OpenSpec plan using its current fingerprint:

uv run cronos-ai action --action approve-plan --run <run-id> --target <change-name> --data plan_hash=<fingerprint> --data reviewer=<name>

Retry an eligible failed task within the configured attempt limit:

uv run cronos-ai action --action retry-task --run <run-id> --target <task-id>

Resolve merge conflicts

Resolve and stage the files in the run worktree, then record the resolution:

uv run cronos-ai action --action resolve-conflict --run <run-id> --target <task-id> --data "resolution=Describe the resolution"

Review a run

Inspect a review packet's diff and verification evidence:

uv run cronos-ai review --run <run-id>

Approve the current run-level review using its fingerprint:

uv run cronos-ai action --action approve-review --run <run-id> --target run --data review_hash=<fingerprint> --data reviewer=<name>

Reject it with a rationale to return eligible tasks to remediation:

uv run cronos-ai action --action reject-review --run <run-id> --target run --data review_hash=<fingerprint> --data reviewer=<name> --data rationale="Describe requested changes"

Review actions must reference the current review fingerprint and reviewer.

Inspect past action outcomes with:

uv run cronos-ai actions

See the task states and review details for retry limits and approval behavior.

Task states and human attention

StateMeaningHuman attention
queuedWaiting for dependencies or scheduling.Dependency-only waits are not human blockers.
readyEligible for a worker or remediation assignment.Not a blocker by itself.
runningAssigned to an active worker.Herdr reports Working.
integratingWorker finished successfully and its branch awaits integration.Not a human blocker.
waiting for humanRequires clarification or an approval decision.Appears with the reason and next action.
blockedCannot proceed, for example because of a merge conflict.Appears with the reason and recovery action.
failedExecution stopped after a failure.Retry is offered only below the configured attempt limit.
reviewIntegrated and available to downstream tasks, awaiting run-level review.Appears after a review packet is ready.
doneHuman-approved review completed for the task.Herdr shows the Done label.

FactoryConfig.max_attempts defaults to three attempts and bounds transient retries and remediation assignments. A retry action never increases or resets that limit. Exhausted retries show a policy-escalation step instead of offering an out-of-policy retry.

Failed or inconclusive CI/CD workflows appear in the attention queue and are never considered delivered. Review packets require at least one automated check and one user-perspective scenario result. Failed checks, failed scenarios, or blocking review findings create a blocked packet and return eligible tasks to remediation.

A human decision applies only to the latest packet and only while its integrated diff and evidence fingerprints remain unchanged. The delivery gate remains closed after rejection, missing evidence, a changed diff, or an inconclusive review.

The default state directory is $XDG_STATE_HOME/cronos-ai when XDG_STATE_HOME is set, or ~/.local/state/cronos-ai otherwise. Set CRONOS_AI_STATE_DIR to use a different location.

The previous AI_SOFTWARE_FACTORY_STATE_DIR variable is not honored. Set CRONOS_AI_STATE_DIR to your existing custom location if you used the old variable.

Request submission and human actions are durable even if the controller is stopped. The controller can be stopped with Ctrl+C, and its process lock is released on exit. To restart it, run the same command with the same state directory. Queued requests and human actions remain in factory.sqlite3 and are visible after restart without being re-enqueued by controller startup. Use cronos-ai status with the same --state-dir to inspect the recovered queue.

06 · Specialist components

Worker execution and integration components

The worker path is assembled from Python APIs rather than started by cronos-ai run.

  • TaskWorktreeManager creates a branch and isolated Git worktree for each attempt.
  • FactoryProfileRegistry resolves only explicitly approved skills, MCP tools, models, provider-key environment names, and network origins.
  • PiWorkerExecutor supervises Pi RPC through a reusable Herdr pane and the configured sandbox adapter.
  • TaskIntegrator merges dependency-ready task branches into the run branch and leaves conflicts for a human to resolve.

The Docker adapter mounts only the task worktree, injects the configured provider key, and fails closed when sandbox requirements are unavailable.

Do not mount host authentication directories or treat repository-provided skills, extensions, MCP servers, or webhook text as trusted resources.

See the sandbox security and recovery details and worker resource configuration.

07 · External signals

Webhooks and delivery

WebhookEndpoint is a WSGI application that an operator can mount at POST /webhooks/<source-id>. Each source requires an explicit repository allowlist and a distinct signing secret.

The handler authenticates and deduplicates events, then WebhookIngestor applies normal clean-repository OpenSpec intake before creating a monitoring request. Alert text remains untrusted triage input and cannot directly execute commands or bypass approvals.

There is no built-in network listener, hosted relay, production CI/CD provider, or provider credential configuration.

DeliveryCoordinator accepts an injected CIAdapter only after a human approves an unchanged review packet. Only an authoritative successful workflow result counts as delivery.

See the webhook and delivery adapter details.
