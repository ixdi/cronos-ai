MVP integration note

This repository provides the intake server, workflow functions, runtime adapters, and operator CLI, but not a single bundled service/worker launcher. The intake example below only queues tasks; a host composition must also run reconciliation and the workflow worker before tasks execute. See Core workflow for that boundary.

01 · Overview

What Cronos does

Cronos is a local-first, human-supervised software factory. It turns a task description into a traceable workflow rather than letting one agent make unreviewed changes directly in the shared repository.

Agents do the work

Jev classifies requests. Pi coding roles implement, review, verify, and document work in an isolated task environment.

People own decisions

An operator inspects the result, approves it, or rejects it with feedback. Only approval advances the task to documentation and PR delivery.

Cronos persists queue entries, workflow status, agent events, workspace identity, and LangGraph checkpoints in SQLite. On restart, active work is marked interrupted; Cronos never resumes it automatically.

02 · The task lifecycle

How a task moves through Cronos

  1. Intake and queueA local client submits a JSON description to the loopback-only POST /tasks endpoint. SQLite stores it as queued.
  2. TriageJev classifies the request. Only auto_resolvable continues in this MVP; clarification and specification paths are blocked with a reason.
  3. Isolated implementationThe workspace provider creates a task-specific Git worktree and Docker runtime. Pi implementation tools modify task files, not shared Git history.
  4. Automated checksCode review and verification run with read-only tools. A failed quality gate stops the workflow and records the outcome.
  5. Human reviewThe operator reads the result. Rejection sends feedback to implementation and repeats review and verification.
  6. Documentation and deliveryApproval permits documentation. The host—not the agent—stages and commits changes, pushes a repository-scoped branch, creates a GitHub PR, and records the PR reference.

03 · Before you start

Prepare your local environment

For a real agent run, the Cronos host needs Bun, Git, Docker, and a working Herdr CLI/local service. The target source must be a Git repository with the configured base branch available.

The runtime image is supplied by the operator; Cronos does not build it. It must include sh, Git, Bun, Node.js 22.19 or newer, and Pi CLI. Pi uses a configured chat model. Jev is used only as the triage classifier through Pi's codemode tool.

Start with the repository checks

From the repository root, install the locked workspace dependencies and run the tests before configuring any real credentials.

Terminal · repository root
bun install --frozen-lockfile
bun test
bun run --filter cronos-panel start -- --help

The regular test suite uses fake agents and providers. An opt-in Herdr/Docker integration test is documented in the runtime guide; it does not make real model calls.

Set the host environment

Set deployment values in your shell or secret manager. Keep CRONOS_RUNTIME_ROOT outside the source repository when possible, and never commit populated credentials.

The triage classifier requires Jev/TypeSafe credentials in the environment passed to the runtime. The selected chat provider may require its own key as well. Add only the names needed to CRONOS_RUNTIME_ENV; do not forward host credentials wholesale.

For approved GitHub delivery, configure CRONOS_GITHUB_OWNER, CRONOS_GITHUB_REPOSITORY, CRONOS_GITHUB_APP_ID, CRONOS_GITHUB_INSTALLATION_ID, CRONOS_GITHUB_REPOSITORY_ID, and CRONOS_GITHUB_APP_PRIVATE_KEY. Follow the GitHub App setup instructions; the App should have only Contents and Pull requests write permissions on the one target repository.

05 · Intake

Submit local work

The intake server binds to 127.0.0.1, accepts JSON with a non-empty description, and rejects bodies larger than 64 KiB. Run the following in a host process to open the API:

Terminal · starts intake only
bun -e '
import { createIntakeServer } from "./cronos-core/src/intake-server.ts";
import { openStorageDatabase } from "./cronos-storage/src/database.ts";

const db = await openStorageDatabase(Bun.env.CRONOS_DB_PATH ?? "./cronos.sqlite");
const port = Number(Bun.env.CRONOS_INTAKE_PORT ?? "3000");
const server = createIntakeServer(db, port);
console.log(`Cronos intake listening at ${server.url}`);
'

With the host process running, submit work from the same machine:

Terminal · queue a task
curl --fail-with-body \
  -X POST http://127.0.0.1:3000/tasks \
  -H 'content-type: application/json' \
  -d '{"description":"Implement the first feature"}'

A successful request returns HTTP 201 with the new task ID and queued status. Use the ID in the CLI commands below. The intake process alone only queues; the MVP currently has no packaged worker launcher to claim and execute that task.

Keep intake private

This endpoint has no network authentication or rate limiting. Do not bind it to a public interface, expose it through a reverse proxy, or port-forward it beyond the local machine.

06 · Operator CLI

Inspect tasks and workflow results

The cronos-panel package is a JSON CLI. It reads the shared SQLite database and reports status, workflow stage, errors, agent history, and recent review/verification results.

Terminal · inspect the queue
# All tasks
bun run --filter cronos-panel start -- --db ./cronos.sqlite list

# Only interrupted work
bun run --filter cronos-panel start -- --db ./cronos.sqlite list --status interrupted

# Full details for one task
bun run --filter cronos-panel start -- --db ./cronos.sqlite show <task-id>
StatusMeaningOperator action
queuedAccepted and waiting for a workflow to claim it.Wait for a configured host worker.
activeA workflow currently owns the task.Inspect; do not start a second task.
review_pendingAutomated stages passed and a human decision is required.Inspect, then approve or reject with feedback.
interruptedActive work was stopped during restart reconciliation.Inspect the reason; explicitly resume if safe.
blockedTriage chose an unsupported clarification/specification route.Read the stored reason; resolve manually or resubmit when supported.
erroredA workflow or quality gate failed.Read the failure and agent output before deciding next steps.
deliveredGitHub confirmed PR creation and the reference is stored.Continue PR review in GitHub; Cronos does not track later events.
07 · Human decisions

Approve or request rework

Before approval, inspect show <task-id> for the implementation summary, changed files, code-review output, verification output, and persisted workflow stage.

Approve

Approval resumes the saved workflow through documentation and, with GitHub delivery configured, creates a task branch and pull request.

CLI
bun run --filter cronos-panel start -- --db ./cronos.sqlite approve <task-id>

Reject with actionable feedback

Rejection returns work to implementation and repeats review and verification. Be specific about expected behavior or missing cases.

CLI
bun run --filter cronos-panel start -- --db ./cronos.sqlite reject <task-id> \
  --feedback "Handle the empty input case"

Approval is valid only for a task in review_pending. The CLI runs the workflow action in the host process; actions may take as long as the agent roles they start.

08 · Recovery

Recover after a restart

Startup reconciliation marks previously active tasks interrupted and stops their runtime without deleting the task worktree or checkpoint. A task already awaiting human review remains review_pending.

  1. List interrupted tasks and inspect the error/stage with show <task-id>.
  2. Confirm the repository and task worktree still exist and that resuming is appropriate.
  3. Run explicit resume. Cronos requires both a matching persisted workspace handle and LangGraph checkpoint.
Terminal · explicit recovery
bun run --filter cronos-panel start -- --db ./cronos.sqlite show <task-id>
bun run --filter cronos-panel start -- --db ./cronos.sqlite resume <task-id>

If the checkpoint or matching workspace is unavailable, the task remains interrupted and the CLI reports why. Resume does not create a fresh worktree silently.

09 · Pull requests

Deliver approved changes to GitHub

The delivery service creates a host-owned staging clone, commits the task output outside the agent container, pushes a branch, and opens a PR against CRONOS_BASE_BRANCH (default main). SQLite records the PR number, URL, branch, and delivered status.

Use a GitHub App installed on only the target repository. Cronos requests short-lived installation tokens scoped to that repository with only Contents and Pull requests write permissions. The private key and push token stay on the host and are not passed into agent containers.

10 · Safe operation

Security basics for operators

  • Keep the intake bound to loopback; it is not an authenticated public API.
  • Forward only model-provider environment variable names that the runtime needs. Avoid broad host credentials.
  • Never forward GitHub App private keys or installation tokens into agent containers; the CLI rejects GitHub credential names in the runtime allowlist.
  • Agents can modify task files, but shared Git metadata is mounted read-only. The host owns staging, commits, pushes, and PR creation.
  • Docker isolation is not network-egress isolation. Treat repository content and model output as untrusted, and apply network controls separately if required.
  • Keep database files, runtime worktrees, and secret material out of public web roots and source control.
11 · Troubleshooting

Common questions

My task is queued but no agent starts. Is Cronos stuck?

Not necessarily. This MVP has no bundled always-on worker or one-command service launcher. The intake endpoint only saves the request. A host composition must call startup reconciliation and invoke the core workflow to claim and execute queued tasks.

Why is a task blocked after triage?

The classifier selected clarification or specification work. Those paths are intentionally blocked in this MVP. Inspect the stored reason with show <task-id>; do not expect implementation to start on an unsupported route.

Why did resume fail?

Resume requires the task's persisted workspace identity/path and matching LangGraph checkpoint. If either is missing or mismatched, Cronos fails closed and leaves the task interrupted. Inspect the reported reason; do not manually substitute a different worktree.

Why can't I approve this task?

Approval is accepted only for review_pending. Inspect the current status and workflow stage. An approval that reaches delivery also requires valid GitHub App settings and access to the configured repository.

Does delivered mean merged or CI passed?

No. delivered means GitHub created the pull request and Cronos stored its reference. Cronos does not monitor PR reviews, CI, or merge status after that point.
